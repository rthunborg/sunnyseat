# Vendored Claude Design — ESLint audit

**Date:** 2026-05-08 (revised in Story 1.6 review Round 2, R2-P3 sed-scope correction)
**Story:** 1.6 Task 8 (AC6) + Round 1 review + Round 2 R2-P3
**Trigger:** AC6 of Story 1.6 requires the `globalIgnores` glob in `nextjs-app/eslint.config.mjs` covering `docs/design/references/claude-design/**` to be backed by data — *categorise* the masked violations rather than mask blindly.

This file is the durable artefact justifying the ignore. It is **not** regenerated by `scripts/fetch-claude-design.sh`; only re-author it when the upstream bundle structurally changes (e.g. a new prototype variant added, or a switch from `<script type="text/babel">` to a real bundler).

## Method

1. Temporarily commented out `'docs/design/references/claude-design/**'` from `globalIgnores`.
2. Ran `npx eslint . --quiet > eslint-audit.txt` from `nextjs-app/`.
3. Categorised every violation by `rule-id`. No violation is in more than one bucket.
4. Restored the ignore with an updated code comment that links here.

## Conclusion

After the Story 1.6 review D3=A entity-escape sweep (sed scope corrected by Round 2 R2-P3), all 326 remaining violations are intentional consequences of the prototype's plain-HTML / Babel-standalone authoring style. The 2 trivial JSX entity escapes that were originally cost-deferred have been resolved upstream via a literal-substring `sed` substitution in `scripts/fetch-claude-design.sh` targeting only the two known files; future bundle refreshes carry that fix forward automatically without risking comment or string-literal corruption.

The `globalIgnores` glob `docs/design/references/claude-design/**` therefore remains in `nextjs-app/eslint.config.mjs` for the structural buckets (cross-file refs, design-fidelity click-on-`<div>`, demo-state hook usage), with a code comment pointing to this audit file so future agents understand which errors are intentionally suppressed.

If a future bundle refresh introduces a new rule violation that this audit does not cover, the next agent should:
1. Re-run the audit method above.
2. Either categorise the new violation into one of the existing buckets, or add a new bucket here with a verdict.
3. Update the audit date and the totals.
