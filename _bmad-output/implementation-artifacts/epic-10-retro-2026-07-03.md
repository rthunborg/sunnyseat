## 2. What Went Well

- **The engine-then-UI-then-refine sequencing (10.1→10.2→10.3→10.4→10.5) held cleanly with no rework.** Each story's ratified decisions (the `CLOUD_GATE_THRESHOLD_PERCENT=80` constant, the `applyCloudGate` shape, the never-`?? 0` unknown-cloud discipline, the `effectiveCloudCover` split) were treated as fixed by every downstream story — 10.3 and 10.4 changed only the *input* to the gate, never the threshold or the switch logic, exactly as the 10.1 `// SEAM for Story 10.3` comment promised.
- **The two-signal guarantee (geometric layer sacred) was protected by construction, not just by review.** Every story independently reaffirmed "do NOT touch `sunExposurePercent`/`sunWindow`/`peakTime`," and 10.5 closed the loop with a net-new cross-tier test proving those fields are byte-identical across all five weather variations for the same geometry+instant — the exact invariant the epic exists to protect, and one no single-tier test had pinned before.
- **The "unknown ≠ 0, unknown ≠ 100" discipline propagated cleanly across three independent data sources** (total cloud cover in 10.1, per-layer cloud cover in 10.3, precipitation rate in 10.4) without a single regression — each new field followed the same `undefined`-never-fabricated pattern established in 10.1 AC2.
- **A real cross-story defect was found and root-caused, not just patched around.** 10.4's code review caught a unit test silently issuing a live outbound fetch to `api.met.no` (masked by the client's own error-swallowing), and the fix was escalated in the epic-10 retro-notes from a one-file patch to an epic-wide shared-test-setup guard, which 10.5 then implemented (`test/setup/setup.ts`) — closing a whole class of future masked-live-call regressions, not just the one instance.
- **The `never`-exhaustive-switch discipline caught the union extension cleanly at compile time** — 10.1's `tsc`-forced sweep of `VenueSunStatus` consumers found every render/rank/aria site with zero runtime NaN or thrown switch, and every subsequent story's new switches followed the same pattern.
- **The EOL/CRLF landmine in `confidence-calculator.ts` was diagnosed once (10.1) and then defused proactively by every later story that touched the file.** 10.1 lost a review round discovering the root cause (mixed-EOL committed blob, not tabs-vs-spaces); 10.3 pre-emptively reconstructed the file from the parent blob and got a clean single-hunk diff on the first pass; 10.4 correctly predicted it would not need to touch the file at all and didn't.
- **Honest handling of what a dev agent cannot self-fabricate.** 10.5 explicitly refused to invent a live-sky observation for AC2 or self-bless the missing 10.2 obscured reference PNGs, instead producing a precise, ready-to-execute maintainer protocol (exact URLs, coordinates, comparison table) — mirroring the Epic-9 precedent (9.10's physical-device spot-check) rather than fudging a "PASS."
- **The 10.3 physics decision (thin cirrus ≠ blocking stratus, weight ≈0.25 vs 1.0) was designed, documented with rationale, and pinned with relative-boundary tests** (100%-high does not gate, 100%-low does) rather than brittle exact-number assertions — deliberately built to survive a future weight re-tune.

## 3. What Was Hard

- **A genuine cross-story integration gap slipped past every single-story consumer sweep.** 10.1's Task 1 swept every *render/compile* consumer of `VenueSunStatus` to a compile error, but the epic-review pass found `CloudObscured` is rejected by the feedback API's Zod enum AND the live Supabase `CHECK` constraint on `predicted_state` — neither surfaced by `tsc` because `as const satisfies X[]` checks membership, not exhaustiveness, and neither the Zod schema nor the DB constraint is a compile-forcing site. This means CloudObscured feedback inserts silently fail on the live path today; the story-provided SQL migration (`10-1-feedback-cloudobscured-check.sql`) fixes it but has not been applied to live Supabase yet.
- **The displayed-confidence coverage cap flattened the very signal 10.1/10.3 built.** 10.5's AC4 regression pass found the "100%-cloud confidence < 0%-cloud confidence" invariant reads as FALSE at the engine's *displayed* output (both clip to exactly 60) for any venue whose shadow-data coverage status is `'unknown'` — which is every launch venue today, since no validation artifact has been loaded. The FR12 cloud term genuinely fires below that cap, so the fix (implemented) genuinely works — but a user will not SEE the confidence number move until a cluster is marked `eligible`. This was correctly diagnosed as a pre-existing Story-3.0.5 cap, not an Epic-10 regression, but it means the epic's flagship "confidence genuinely reflects cloud cover" capability is currently invisible in the UI for 100% of live venues.
- **The Windows-host visual-validation gap from Epic 9 carried forward unchanged and got worse for this epic specifically.** `visual-validate.sh` still cannot run on this machine (retro-note 9-2), and unlike Epic 9's removal/rework stories (which at least had *existing* references to diff against), 10.2 introduced a brand-new visual surface (the obscured fourth state) with NO reference PNG to even attempt a diff against. The muted-in-HUE mitigation (slate vs amber vs grey, verified by numeric contrast + live axe scans) is a reasonable substitute, but the epic genuinely cannot claim a passed visual gate for its main UI deliverable until a maintainer rebaselines two brand-new screens at two breakpoints.
- **The mobile obscured axe scans inherited pre-existing debt rather than being new-state clean.** 10.2 had to leave two mobile obscured a11y scans as `test.fixme`, not because the obscured chrome itself fails contrast (it is AA, verified live on desktop), but because they render underneath the Story-5.1 amber-label venue-card contrast debt that fixmes every mobile card scan — a dependency the story could not resolve within its own scope.
- **10.5's own e2e matrix has an honest, acknowledged coverage gap.** The distinction the entire Tier-1 story (10.3) exists to protect — "high-cirrus-only is NOT gated, low-deck IS gated" — renders byte-identically at the DTO/presentation layer (both are amber "Sunny," the differentiator only shows up as an internal `skyCondition` value the matrix does not assert). The differentiator is correctly guarded at the engine/unit layer, but the flagship e2e matrix would still pass if that scenario were silently dropped or mis-set — a defer, not a blocker, but a real gap in what the "verification pass" story actually verifies end-to-end.
- **Concurrency-sensitive flakiness in `sun-engine.test.ts` was observed across three separate stories (10.1, 10.2) and never root-caused, only worked around.** The same 5-second timeout under full-suite load (isolated runs pass cleanly) was flagged as "pre-existing, watch the CI budget" in three retro-note phases without anyone owning a fix — a candidate for the kind of debt that quietly compounds until CI actually goes red.

## 4. Key Insights

1. **`tsc`-forced exhaustiveness is necessary but not sufficient for union extensions that cross the API/DB boundary.** The `CloudObscured` sweep worked perfectly for every in-process consumer but missed the Zod schema and the live DB `CHECK` constraint precisely because neither is a compile-forcing site. The epic-review's own ratified fix — "exhaustiveness-forcing `Record<Union, true>` on consumer allow-lists + sweep validation layers too" — should become standard create-story guidance any time a future story extends a DTO union: name the validation-layer sweep explicitly, not just the render/compile sweep.
2. **A story that "fixes" a signal deep in the engine does not automatically make that signal visible to users** if an unrelated, pre-existing cap sits between the fix and the display. The FR12 confidence fix (10.1) is correct and tested at the calculator layer, but the Story-3.0.5 coverage cap silently absorbs it for every unvalidated venue. Future engine-layer fixes should include an explicit "does anything downstream clip or override this before it reaches the user" check as part of Definition of Done, not just a unit test at the layer where the change was made.
3. **The two-signal architectural decision (preserve geometry, gate only the headline) was the single highest-leverage design call of the epic, and it held for five stories without erosion.** Every story independently re-derived and re-affirmed the same guardrail from first principles rather than needing it re-explained, and 10.5's byte-identical cross-tier test converts that discipline from "everyone remembered to check" into "a regression is now mechanically impossible to ship silently." This pattern (state the sacred invariant once, ratify it, then have the LAST story in the sequence add the cross-cutting regression test) is worth repeating for any future multi-story epic with a similar "don't let X drift" constraint.
4. **Diagnosing a landmine once and writing down the root cause (not just the symptom) prevents repeat cost.** The `confidence-calculator.ts` EOL story is the clean version of this: 10.1 spent a review round discovering the TRUE cause (mixed-EOL blob, not reindentation), and every subsequent story that had reason to fear the same file either avoided it entirely (10.4) or reconstructed cleanly on the first attempt (10.3). Contrast with the `sun-engine.test.ts` concurrency flake, which was observed three times and never diagnosed — the difference is whether the retro-note captured a root cause or just a symptom.
5. **A dev agent correctly refusing to self-fabricate a live observation or a reference image is a feature of the process, not friction to route around.** Both 10.2 and 10.5 hit maintainer-only steps (reference-PNG rebaseline, live sky spot-check) and handled them identically: precise protocol handed off, zero attempt to force a pass. This consistency across two stories suggests the "dev forbidden from self-blessing" rule is now fully internalized rather than something that needs re-litigating per story.
