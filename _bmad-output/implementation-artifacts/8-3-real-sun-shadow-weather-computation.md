## Story

As a **user**,
I want sun status, sun windows, confidence, and uncertainty to be computed from the real engine,
So that the predictions I see are trustworthy.

## Acceptance Criteria

1. **Real engine produces the sun-output fields through the unchanged DTO.**
   **Given** `lib/solar` (sun position + shadow casting via `get_buildings_near_point`) and `lib/weather` (Met.no Locationforecast)
   **When** a venue's sun data is computed for the requested time
   **Then** `currentSunStatus`, `sunExposurePercent`, `sunWindow`, `confidence`, and `predictionUncertainty` are produced from the real engine and serialized through the existing DTO fields

2. **Empty/low shadow-caster coverage caps confidence and renders uncertainty copy (Story 3.0.5/3.0.6 contract).**
   **Given** the Story 3.0.5/3.0.6 confidence contract
   **When** shadow-caster coverage is empty or below threshold for a venue
   **Then** confidence is capped/marked rather than reported as confidently sunny, and the public uncertainty copy renders via the existing `next-intl` keys without leaking geodata internals

3. **Freshness metadata reflects real weather (Story 2.6 contract).**
   **Given** the sun-freshness metadata contract (Story 2.6)
   **When** the response is built
   **Then** `sunDataSource`/`weatherUpdatedAt` reflect real weather freshness so the confidence display's exact/approximate/hidden states behave correctly

4. **Env-gated, CI dependency-free, gate-stable (Epic-8 contract — established by Stories 8.1/8.2).**
   **Given** the real engine is opt-in behind an env flag and the default path keeps the 8.2 seed values
   **When** the flag is **unset** (CI / tests / visual gates)
   **Then** `/api/venues` and `/api/venues/[slug]` return the **byte-identical** seed output of today (the five visual references + `map-primary`, the real-route Playwright specs, and the Vitest route tests stay green with **no live Supabase/Met.no dependency and no rebaseline**); and **when** the flag is `real`, the routes compute every sun-output field from `lib/solar` + `lib/weather` for the requested time/location, inheriting the 3.0.5/3.0.6 caps — **no DTO shape change, no frontend component change, no `_state`/URL/query-key/cache contract change.**

## Dev Notes

### The 8.2 → 8.3 seam (read this first)
Story 8.2's `8-2-real-venue-store-api.md` "The 8.2 ↔ 8.3 scope seam" is the contract you are completing. `VenueDataDto` carries two kinds of fields:
1. **Durable venue attributes** — `id`, `venueId`, `venueName`, `venueSlug`/`slug`, `neighborhood`, `location`, `isPartner`, `thumbnail`, and detail (`description`, `address`, `openingHours`, `peakTime`, `shadowWarningMinutes`). **8.2 made these real (the `venues` table). Do not touch them.**
2. **Sun-engine outputs** — `currentSunStatus`, `skyCondition`, `confidence`, `sunExposurePercent`, `sunWindow`, `predictionUncertainty` — plus the response `meta` freshness (`sunDataSource`, `weatherUpdatedAt`). 8.2 carried these as **TEMP seed values on the `venues` row / fixture**. **This story replaces them with the real engine.** The 8.2 contract artifact marked those columns *"TEMP seed — superseded by Story 8.3"*; you may leave the columns in place (the default seed path still reads them) — dropping them is optional cleanup that belongs with the live cutover (8.5).

### Engine surface (verified read of `nextjs-app/lib/solar` + `lib/weather`)
- **Public API** is re-exported from `lib/solar/index.ts`.
- **`calculateSolarPosition(utc: Date, lat?, lng?): SolarPosition`** (`solar-calculation-service.ts:6`) — NREL SPA; `isSunVisible`, `elevation`, `azimuth`. `getSunTimes(dateStr, lat?, lng?)` gives sunrise/sunset. `calculateSolarTimeline(start, end, intervalMs, lat?, lng?)` for sampling. **Do not modify this math.**

### DTO mapping rules (target shapes — `lib/types/api.ts`)

### Pipeline injection seam (where seed values are replaced)
Both routes run `getVenues()`/`getVenueBySlug()` (`venue-store.ts`) → `normalizeVenueForResponse` → `applyFixtureWeatherAvailability` → `applyPlannerSelectionToVenue` → distance/filter/sort/slice. Today the sun fields originate as **seed values on the `StoredVenue`**. Inject the real engine so that, with the flag on: (1) sun-output fields are replaced **before** `normalizeVenueForResponse` (so it still sanitizes them) and **before** the `SUN_STATUS_ORDER` sort; (2) `applyPlannerSelectionToVenue` and `applyFixtureWeatherAvailability` are **bypassed** (engine handles requested time + real freshness).
