### Review Findings

- [x] [Review][Defer][Med] Rain-gated outcome is cached for a 15-min bucket despite a ~5-min radar cadence — `computeRealSunEngineResult` returns `cacheable: buildings !== null` (`nextjs-app/lib/services/sun-engine.ts:632`) with NO near-now/rain exclusion, so a `CloudObscured`-because-raining outcome (and, symmetrically, a `Sunny` cached just before a shower) is pinned to the 15-min `SUN_COMPUTE_CACHE_TTL_MS` bucket (`nextjs-app/lib/services/sun-engine-cache.ts:40`). The nowcast's deliberately-short `next:{revalidate:60}` HTTP TTL is defeated by the engine-level outcome cache in front of it, so near-now rain can be shown stale for up to ~15 min. Flagged independently by blind@primary, blind@secondary and edge@primary. The worst-case staleness equals one slider bucket and matches the sun-freshness horizon the app already accepts, so this may be an intended tradeoff rather than a bug — it needs an intent call. Recommended: defer: accept the one-bucket (~15 min) staleness as consistent with the existing sun-freshness horizon and log a follow-up to exclude `isNearNow` rain-gated outcomes from the compute cache (`cacheable: buildings !== null && !isNearNow`) only if live spot-checks show the stale-rain window is user-visible. [auto-resolved: deferred per triage recommendation — epic mode]

- [x] [Review][Decision][Low] Rain gate fires on any strictly-positive radar rate with no trace-rain floor — `isRaining = precipitationRate !== undefined && precipitationRate > 0` (`nextjs-app/lib/services/sun-engine.ts:532`) means radar drizzle of ~0.01 mm/h flips a fully-sunlit terrace to `CloudObscured`, whereas cloud has a tunable, documented 80% threshold. Flagged by blind@primary. This is a faithful literal implementation of the epic's "never claim full sun while it's raining" principle, so whether a light-rain floor is desirable is a product judgment, not a code defect. Recommended: dismiss: the epic's "rain wins" intent explicitly sanctions any positive rate; a trace-rain floor is a future tunable, not a defect — leave `> 0` as-is. [auto-resolved: dismissed (won't-fix) per triage recommendation — epic mode]

- [x] [Review][Patch][High] `CloudObscured` feedback submissions are rejected by the feedback API Zod enum and the DB CHECK constraint [nextjs-app/app/api/venues/[slug]/feedback/route.ts:18] — On the live real-engine path `venue.currentSunStatus` can be `'CloudObscured'`; `feedback-session.ts:41` stores it as the detail-view `predictedState` and `FeedbackFlow.tsx:220,243` POSTs it. But `PREDICTED_STATES = ['Sunny','Partial','Shaded','NoSun'] as const satisfies VenueSunStatus[]` (`route.ts:18`) omits `CloudObscured`, so `predictedState: z.enum(PREDICTED_STATES)` (`route.ts:25`) returns a 400 (surfaced to the user as a feedback-flow error). Independently, `3-2-feedback-contract.sql:17` `check (predicted_state in ('Sunny','Partial','Shaded','NoSun'))` would reject it at the DB layer even if Zod were fixed. `satisfies VenueSunStatus[]` checks membership but NOT exhaustiveness, so `tsc` never flagged the missed consumer — Story 10.1's consumer sweep listed `FeedbackFlow`/`feedback-session` as "compiles and doesn't crash" but never reached the HTTP boundary. Fix: add `'CloudObscured'` to `PREDICTED_STATES` (making the array exhaustive over `VenueSunStatus`) AND to the `predicted_state` DB CHECK (`3-2-feedback-contract.sql:17`); add a route test asserting `predictedState: 'CloudObscured'` is accepted. Source: auditor@secondary.

- [x] [Review][Patch][Med] Server-side list sort ranks `CloudObscured` by a fixed status tier and truncates high-solläge obscured venues before the client's solläge-aware re-sort can recover them [nextjs-app/app/api/venues/route.ts:66] — `SUN_STATUS_ORDER` fixes `CloudObscured:2` (below every `Partial:1`) and the route sorts by it then `.slice(0, MAX_RESULTS=50)` (`route.ts:310-317`) BEFORE the response is sent. The client `getVenueSunRankForList` (`VenueList.tsx`) re-ranks obscured continuously as `(percent/100)*2`, so a 95%-solläge obscured venue is `1.9` (above Partial) on the client but `2` (below Partial) on the server. For any query returning >50 matches, a high-solläge obscured venue can be truncated out of the top-50 before the client ever sees it — contradicting Story 10.2 AC2 ("Mest sol ranks by geometric solläge under overcast"). Story 10.2 refined only the client rank and left the 10.1 server sort (and its stale "10.2 refines list ranking" comment) untouched. Masked in the UI today (live venue set < 50), but the two schemes genuinely disagree. Fix: make the server `.sort()` use the same solläge-aware `CloudObscured` rank as `getVenueSunRankForList` (percent-scaled), so the pre-slice order and the client order agree; update the stale `SUN_STATUS_ORDER` comment. Source: auditor@primary+auditor@secondary+edge@secondary.

- [x] [Review][Patch][Low] `SKY_CONDITIONS` DB allow-list drifted out of sync with the `'rain'` value 10.4 introduced [nextjs-app/lib/services/venue-store.ts:357] — 10.1 correctly extended the sibling `SUN_STATUSES` allow-list with `'CloudObscured'`, but the parallel `SKY_CONDITIONS = ['clear','partly-cloudy','overcast','unavailable']` never gained `'rain'`. `coerceSkyCondition` (`venue-store.ts:500-502`) drops any value not on the list to `undefined`. No live-path defect today (skyCondition is computed at request time and merged AFTER `fromVenueRow`, so `'rain'` reaches the UI intact), but if a `'rain'` skyCondition is ever persisted and re-read it is silently stripped to `undefined` (→ no sky line). Closes a real vocabulary drift the epic's own 10.1 consumer-sweep discipline demands. Fix: add `'rain'` to the `SKY_CONDITIONS` array. Source: auditor@primary+auditor@secondary.
