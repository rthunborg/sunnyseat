## 2. What Went Well

- **The prelude caught three wrong planning assumptions before they shipped.** `byggnad_kn1480.gpkg` was 2D-footprint-only (not height data); Baskarta is an XYZ object inventory (not "3D building linework"); and empty shadow-caster coverage was silently reading as high-confidence sun. All three were corrected in 3.0.2–3.0.7 and *proven still-fixed* by Story 3.4's audits.
- **Lessons became tripwires, not just notes.** Each recurring defect class got a regression pin: the routing-boundary scan test, sv/en parity test (now incl. ICU placeholder parity), the forced `_state=` convention for unreachable UI, and the slot architecture for inline flows.
- **Architecture patterns compounded.** Slot-based composition (`feedbackSlot`/`reviewSlot`), server-only persistence adapters with fixture defaults, and the shared Amber CTA meant 3.3 rode on 3.2's rails and 3.4 closed in a single review round.
- **Story-file discipline paid off.** 3.4 — drafted after the story-file-audit tightening — landed 11 review patches same-day in one round.

## 3. What Was Hard

- **Scope tripled (4 → 12 stories)** because the data foundation wasn't trustworthy. Not waste — but a signal that data-source contracts must be validated *before* feature work, not during it.
- **Schema/data stories needed the most review rounds** (3.0.2 ×3, 3.0.7 ×2): nulls, constraint ordering, privilege guards, active-row safeguards, Z-geometry preservation. Multi-round was the cost of getting a durable contract right.
- **Recurring defect classes** across feature stories: invented/stale confidence values, accessibility live-region/duplicate-ID slips, cache-invalidation timing, and i18n fallback hygiene. All eventually pinned, but they recurred because the same surfaces were touched repeatedly.

## 4. Key Insights

1. **Upfront data-contract validation is cheaper than mid-feature discovery.** The prelude delay bought correctness the 3.4 audits later confirmed.
2. **The biggest gap isn't any single epic — it's that the whole app is still fixture-backed.** Real venue + sun/shadow data (the Supabase + `lib/solar` pipeline the prelude made trustworthy) is *not wired into the frontend yet*, and no epic owned that swap. This is now the new "Wire Real Data" epic.
3. **The live database contradicted the "never been live" mental model.** It still carries the original backend build: 177k `buildings` rows, a legacy PascalCase `feedback` table, retired admin tables with data, and pre-existing security-advisor findings. Reconciling the DB with the rebuild is real work that belongs to the data epic.

## 6. Database Application Outcome (Supabase `hhnbxrhfhlzxgllxukzj`)

**Applied (additive, conflict-free, verified):**
- `shadow_casters` + `shadow_caster_import_batches` tables (Story 3.0.2 contract), 15 active-row check-constraints.
- `get_buildings_near_point` RPC recreated against `shadow_casters` (did not previously exist; returns 0 rows against the empty table, as designed; `search_path` set so it is advisor-clean).
- `reviews` table (Story 3.3 contract).
- RLS enabled on all three new public tables (deny-by-default; `service_role` bypass for server-only writes).
- Security advisor: new tables show only INFO `rls_enabled_no_policy` (expected).

**NOT applied — folded into the Wire Real Data epic (see action items):**
- **`feedback` (Story 3.2 contract) — schema conflict.** A legacy PascalCase `feedback` table already exists (`Id`/`VenueId`/`WasSunny`/`IpAddress`, 0 rows); `CREATE TABLE IF NOT EXISTS` would silently no-op and the new persistence adapter could not write to it. Needs rename-to-legacy + create-contract (or equivalent) — a decision for the data epic, where persistence also gets switched on.
- **`shadow_casters` bulk import handoff** — uses client-side `psql \copy`; bulk geodata load (incl. migrating the 177k `buildings` → `shadow_casters`) belongs to the data epic.

**Pre-existing security findings (not introduced here, surfaced by the advisor):**
- ERROR: `public.spatial_ref_sys` RLS-disabled (PostGIS system table).
- WARN: `postgis` extension in `public`; mutable `search_path` on several legacy functions; public INSERT policies on legacy `feedback` and `venue_confirmations`; anon-executable `SECURITY DEFINER` `rls_auto_enable()`.
- Retired admin surface still present with data: `admin_users` (1 row), `venue_confirmations` (2 rows), `admin_actions` (0). Story 3.0 deliberately left dropping these to a manual decision.
